Object storage is significantly better suited than traditional block storage for managing millions of user-uploaded photos due to fundamental differences in data organization. Block storage divides data into fixed-size blocks managed directly by the operating system, which is effective for structured tasks such as running databases or booting virtual machines. However, this approach does not scale efficiently for large volumes of unstructured files. In contrast, object storage treats each photo as an independent object with associated metadata and a unique identifier, stored within a flat namespace and accessed via HTTP rather than a fixed file path. This architecture enables near-unlimited scalability by allowing the addition of more storage nodes, avoiding constraints imposed by partition sizes or file-system limits on individual disks.

Docker made deploying this kind of infrastructure dramatically simpler. Instead of manually installing MinIO and configuring its dependencies from scratch, I was able to pull a pre-built image and spin up a fully working, S3-compatible storage server with a single command. Passing in environment variables like MINIO_ROOT_USER and MINIO_ROOT_PASSWORD handled authentication instantly, and mapping ports 9000 and 9001 exposed the API and web console without any extra networking setup — a good example of how containers make complex deployments reproducible and fast.

In this context, a "bucket" serves as the top-level container for objects. While conceptually similar to a folder, it is structurally flat, lacking a true subfolder hierarchy, despite tools displaying prefixes that resemble paths. Buckets are also the primary location for setting access permissions, which is why creating a dedicated client-photos bucket was appropriate for isolating this client's data.

On a larger scale, enterprise companies protect object storage from server failure through techniques like replication across multiple physical servers, erasure coding (which splits data into fragments with built-in redundancy so it can be rebuilt even if pieces are lost), and distributing copies across separate data centers or availability zones so no single point of failure can take the data down.
